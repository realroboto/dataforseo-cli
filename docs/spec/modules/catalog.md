# Catalog module

1. **Catalog** — the spec as a command tree.
   - Interface: open the newest spec (cache or snapshot); resolve command words to a level or an endpoint; give the schema of an endpoint; search endpoints; report the spec identity.
   - Spec source: `openapi_specification.yaml` on `master` of `dataforseo/OpenApiDocumentation`, no SHA pin (34:87).
   - Daily check: at most once per 24 h (34:88). **Refinement (agent design, 2026-11-07).** Step 1: conditional GET (`If-None-Match` with the last ETag) of the GitHub commits API for the spec file, which gives the newest commit SHA and date. Step 2, only when the SHA is new: GET the raw file at that SHA, gzip. Reason: identity needs SHA and date (34:92), but the raw file's `etag` is a content hash with no commit (checked 2026-11-07: `etag` is a 64-hex value; the commits API gives `55a4ed0 2026-10-26T09:02:05Z`). Fetching by SHA also removes a race between the two reads. Limit: 60 unauthenticated GitHub API calls per hour per IP (r34:11); one a day is far below it.
   - A failed check keeps the current spec and warns once on stderr. It is retried after 1 h, not on every command. A failed fetch never overwrites the cache (34:90). Agent design. Reason: an outage must not add a warning line to every command.
   - Cache: the parsed and checked spec as JSON in the config dir, atomic write, file 600, dir 700 (34:89). JSON parses in about 9 ms against about 400 ms for YAML (r34:58).
   - Structural check before swap: the spec parses; one method per path; path parameters only; POST body = array of task objects; command words are unique and do not clash with hand-written commands (root words `schema`, `search`, `store`; level word `+run`; root and module word `+collect`; the same word deeper in a path, e.g. `content_analysis search live`, is no clash); the path count does not fall by more than 10 % against the spec in use (34:162). On failure dfs keeps the previous spec and warns (34:90).
   - Spec snapshot: generated, never edited by hand. dfs uses the newest spec it has, cache or snapshot (34:91). No exit code for a fetch failure; gapi's exit 4 has no dfs equivalent (34:91; 28:163).
   - **Snapshot source (agent design, refines 34:91 "generated by the build"):** the snapshot is a committed file. It holds the parsed and checked spec as JSON plus its SHA and date, and the network script `pnpm spec:snapshot` writes it (fetch at the newest SHA, structural check, atomic write). `build` copies the snapshot and `spec/overlay.yaml` (Vendor overlay) into the package, and `package.json` `files` lists it. Reasons: `ci.yml` has no network (34:116), but its tests need the full spec (34:121); `dfs --version` needs SHA and date offline (34:92); `spec.yml` diffs against the snapshot (34:106). Pattern: gapi commits the generated output of `pnpm gen:skill` (`google-apis-cli/package.json:18`; writes `skills/gapi/reference/`, `google-apis-cli/scripts/gen-skill.ts:8`). Who runs it: the agent in the drift-fix session (34:107) and the release runbook (step 2). This is **not** the design the owner rejected (34:36; 09:19): there, a manual script was the only way a new spec reached users. Here users get each new spec within 24 h from the runtime check (34:88), and the snapshot is only the tested fallback and the test input.
   - Search: path words, module tag and operation `description` of each path, from the spec only, HTML stripped. In memory, per call; case and diacritics folded; path words weigh more; no Store dependency (34:142–143).
   - Deprecated fields: none in request schemas. The 31 `deprecated: true` properties (r34:20) are all response fields (`scripts/check-vendor-spec.py`, spec `55a4ed0`), so the Planner has no deprecation rule.
   - **Resolution (agent design, 2026-11-07).** Words resolve to the longest spec path they match. A path-parameter slot takes the next word only when that word is not a child word of the node. A node that is both an endpoint and a level runs as the endpoint; its `--help` shows the endpoint and its children. Facts (spec `55a4ed0`, check.py `tree.endpoint_and_level`): `on_page/content_parsing` is an endpoint with child `live`; 15 `locations` endpoints have an optional `{country}` child (`dfs serp google locations` and `dfs serp google locations us`).
   - **Vendor overlay (agent design, 2026-11-07).** The vendor spec has faults: request types that its own docs contradict, and fields its own examples use but its schemas lack. dfs corrects them as data, not as Planner rules: a committed file `spec/overlay.yaml` in OpenAPI Overlay 1.0 format (spec.openapis.org/overlay/v1.0.0), targets only in RFC 9535 normalized-path form (`$['components']['schemas']['X']['properties']['filters']['items']`), actions `update` and `remove`. Each target selects an object or array, as Overlay 1.0 requires ("the target object or array", Action Object `remove`); a target that selects a scalar fails the load. The Catalog applies it to every spec (cache, fetch, snapshot) before the structural check; a target that is not a normalized path fails the load. The snapshot and the cache keep the vendor spec unchanged, so SHA, date and the drift diff stay the vendor's. Reasons: Overlay is the OpenAPI standard for repeatable changes to a spec the user does not own; the normalized-path subset needs no JSONPath dependency; vendor quirks live in one file that `spec:check` keeps honest, not in code. Content for spec `55a4ed0` (check.py): `remove` the `items` schema of the 85 request fields named `filters`, `backlinks_filters`, `initial_dataset_filters` and `relevant_pages_filters` (typed `object` or `string`; real values are `[field, op, value]` arrays, `and`/`or` and nested groups: vendor description of `BacklinksAnchorsLiveRequestInfo.filters`; r20:41); `remove` the `additionalProperties` schema of `BacklinksBacklinksLiveRequestInfo.custom_mode` (its own description shows `{"field": "domain", "value": 100}`); `update` 3 request schemas with the 5 fields their examples use (`dataforseo_labs/google/historical_serps/live`: `datetime_from`, `datetime_to`, `limit`; `backlinks/bulk_new_lost_referring_domains/live`: `datetime_from`; `business_data/google/hotel_searches/live`: `priority`).
